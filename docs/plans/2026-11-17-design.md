# 餐账设计

## 范围
本系统用于自有门店经营分析，接入饿了么/淘宝闪购和京东秒送的授权订单，定时拉取当日数据，支持手动补查；不执行接单、退款、营销操作。

## 架构
FastAPI 提供网页与 REST API，Jinja2 渲染外壳，浏览器使用本地静态资源。SQLAlchemy 负责 SQLite/PostgreSQL；APScheduler 负责定时任务；官方 MCP SDK 暴露同一查询服务。平台适配器只负责请求、验错和标准化，不直接写业务表。

本地支持 `uv sync` 后启动。服务器提供 Docker Compose（应用、独立 worker、PostgreSQL）以及 systemd 示例。同步任务独立于 Web worker，避免多实例重复调度；数据库唯一约束和同步锁保证同一门店任务不重入。

## 数据与口径
门店平台配置精确绑定，不跨门店查找凭证。订单唯一键为 merchant_id + external_id。原行保存原始商品名、份数和平台商品码；组件保存统一商品名、数量、来源（平台、规则、原商品）和原行 ID。结构化子商品优先；规则支持精确名称映射和可预览的分隔符拆分。无法判定时保留原商品并显式标注待确认，不伪造明细。

订单状态和退款记录随着重复同步更新，商品目录支持名称归一。有效销量与实际制作耗料分开：取消且未制作不计有效销量，退款不自动意味着原料回库。第一版展示有效销量、已下单量与退款相关状态，备货预测由 MCP 消费端结合配方和库存完成。

## 页面
工作台、订单明细（展开原行与组件）、商品销量、拆分规则、门店接入、同步记录、MCP 接入说明。页面显示真实空状态和错误状态。显式命令可导入演示数据，演示不作为平台同步的降级路径。

## 部署与权限
网页使用登录会话；MCP HTTP 使用独立 Bearer token。凭证通过环境变量引用，在数据库只保存环境变量名，接口和日志不返回密钥；配置缺失显式失败。服务器部署使用 HTTPS 反代，本地可绑定 loopback。

## 验证
核心数量、套餐拆分、重复同步更新、数据库唯一约束、分页失败、跨店隔离、登录和 MCP 协议必须有自动化测试。浏览器验证新增门店、规则预览、明细展开和筛选。真实平台 API 和 Docker 容器启动属于独立环境验证，不假称通过。
